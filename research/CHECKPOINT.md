## Verified conclusions

1. Atmosphère 1.12.1 and hekate v6.5.4 support firmware 23.0.1. This is firmware compatibility.
2. The OLED uses Mariko/Tegra X1+ hardware. Fusée Gelée (`CVE-2018-6242`) is disproven for this hardware.
3. Patched/Mariko consoles can enter RCM but cannot receive a payload.
4. No publicly documented, reproducible software-only path to Atmosphère was found for an unmodified OLED on 23.0.1. This is an absence-of-documented-method finding, not proof of impossibility.
5. The documented route is a hardware modchip, which is out of scope.
6. `ns2jb` is a real software-only userland/sysmodule chain on Switch 2 23.0.1. It combines a 32-bit integer overflow in the SmileBASIC interpreter with a path-normalization buffer overflow in the `fs` sysmodule. The author says it was **tested on Switch 1 but not packaged**, and it does not provide kernel, bootROM, CFW, or persistence.
7. The packaged `ns2jb` demo requires SmileBASIC 4.4.9, system software 23.0.1, a Node.js 22+ host on the same network, and more than 20 MiB free in the SmileBASIC save. It is tethered and installs no CFW or persistence.
8. SmileBASIC 4 was delisted from the eShop in several regions after the `ns2jb` release, so the documented entry point is only available to people who already own it.
9. GameShare is handled on the receiving system by the **`splay` system applet**, added in 20.0.0. It uses `ldn` local wireless with `SetProtocol` value 3, receives a video stream, and accepts the game NACP and JPEG images during setup. At least some host data, including `AdvertiseData`, is ECC-verified.
10. Only a Switch 2 can host GameShare. A Switch 1/OLED can only receive, and only over local wireless. Nintendo states the feature cannot be used between two Switch 1/OLED/Lite systems.
11. `splay` holds `StreamPlaySaveData` (`FsAccessFlag` bit 47) and, on Switch 1 with 23.0.0+, access to `news:c` and `stpl:sys`. These are applet-level privileges.
12. **No public vulnerability, proof of concept, or exploit** was found for `splay`, the GameShare protocol, or its NACP/JPEG handling. The surface is `UNKNOWN`.
13. A full `splay` compromise would yield applet-level userland code execution, not kernel, bootROM, or Atmosphère.
14. Gezine claims a Switch 1/2 userland exploit that is not WebKit- or save-based and works offline across firmware versions. It is unreleased, has no public technical details, and is `UNVERIFIED`. Gezine also says SmileBASIC 4 is not strictly required, naming Artemis Engine and an undisclosed physical cartridge.
15. CVE-2026-82079 is a local-wireless stack overflow fixed in 23.0.0; the target is reported on 23.0.1. No public exploit code was found.
16. PegaSwitch (early browser) and Caffeine (patched Erista 4.1.0) are historical and do not apply to the target.
17. Switchbrew's 23.0.0 page documents fixes for `bsdsocket`, `audio`, and `ldn`; 23.0.1 lists a stability fix and an `sdb`/SystemVersion update, with an unfilled security-flaw placeholder.
18. Atmosphère is a boot-time CFW, so a software-only path needs **boot-stage execution** (stage 3), not only a userland or kernel primitive. Caffeine proves the category works on patched hardware: a warmboot exploit ran full CFW on patched Erista 4.0.0–4.1.0 without Fusée Gelée.
19. No public Mariko warmboot or pre-Horizon chain exists for modern firmware. Warmboot is package1 section 0, and Mariko package1 is signed and encrypted, so an equivalent would need a code bug in verified warmboot or TSEC code.
20. The `ns2jb` `fs` bug is a privilege-escalation stage, not an entry point: it is reached through an `IFileSystem` handle after the SmileBASIC overflow. Without stage 1 there is nothing to escalate from.
21. SmileBASIC 4 is download-only, so there is no physical cartridge route; the owner does not have it, and the delisting removes the purchase route in several regions.
22. Artemis Engine games can chain-load Lua from an edited save, but the public loader is documented for PS4 and Windows and yields game-script level, not native code. No Switch reproduction is documented.
23. The three sharing paths are distinct. **Virtual Game Cards** require a Nintendo Account, internet, local-wireless proximity, and a server-issued license (`E-079`). **GameShare / `splay`** requires a real Switch 2 host and ECC-verified host data (`E-038`–`E-044`). **LDN pre-auth** is the only one a PC can reach without a second console or Nintendo signing keys. Retail LDN is AES-encrypted and needs `prod.keys`; the no-key plaintext development-mode path was attempted once, plus a 60-second TX diagnostic, but the Phase 2 run is inconclusive because host transmission is unconfirmed (`E-078`). The known LDN CVE (`CVE-2026-82079`) is fixed at 23.0.0, so it is not available on the target. A later prod-mode host run emitted valid AES-CTR advertisements but still produced no join (`E-084`, `E-085`). Run 3 and the adapter controls later showed that monitor-mode injection does not transmit, while AP mode does (`E-089`–`E-091`).
24. The LDN passive path is verified on the target. With the console hosting a Dragon Ball FighterZ local-wireless room, the Archer T3U Plus in an OrbStack Ubuntu VM captured 64 advertisement frames for title `0100a250097f0000`, scene `0`, LDN version `4`, AES-CTR, dominant channel `1`. The plaintext `NetworkId` header was readable without keys. The sanitized record is `research/hardware-observations/2026-10-28-ldn-phase1.json`. Phase 1 transmitted nothing.
25. The Phase 2 plaintext-host run is **inconclusive**. The owner approved one active run; the host started with `--compat-no-active-ack`, advertised for 30 seconds on channel 1, and stopped cleanly. The console showed no room, the host logged no `JOIN`, and no authentication request was observed. `dmesg` reported `failed to get tx report from firmware` after the 2-second and 30-second runs, and the `rtw88_8822bu` driver is reported to fail beacon transmission in AP mode with this error. Host transmission is therefore unconfirmed. The run does not show that retail 23.0.1 rejects security mode 3.
26. The 60-second TX check on 2026-10-28 was **invalid**, not negative. The host advertised for 60 seconds and three CoreWLAN scans from the Mac's built-in Wi-Fi did not show the 32-character SSID. The LDN host beacon uses a 32-byte null SSID (`SSIDElement("\x00" * 32)`), and the real network ID is carried in vendor action frames, which a wildcard Wi-Fi scan does not report. The scan therefore cannot confirm or deny transmission. `dmesg` logged a third `failed to get tx report from firmware` message after the run. A **directed** scan for the known SSID was proposed as a better one-sided check, but it was later found invalid because it returns false positives for non-existent 16-byte SSIDs (`E-086`). A monitor-mode capture on the host interface or a second receiver was the proposed definitive check; the later AP/monitor controls showed that the host's monitor-mode path does not transmit (`E-091`).
27. The owner-provided `prod.keys` decrypt the Phase 1 Dragon Ball FighterZ advertisement. The decrypted payload reports **security mode 1 (prod/encrypted)**, the challenge present, channel 1, band 2.4 GHz, max 2 participants, app version 26, and 4 bytes of application data; the advertisement SHA-256 validates. This confirms the keys match the target firmware's **LDN key derivation** and that the retail room is not a development mode. The keys and firmware dump are local-only and ignored by git. The remaining blocker for a PC-hosted room is the adapter's unconfirmed TX path, not the key gate.
28. The owner's firmware dump is **NCA-only** and its key coverage is incomplete. All 238 NCA headers decrypted as valid NCA3 with the owner's `header_key`. The `ldn` sysmodule is title `0100000000000018`, version `0x5c0004b0` (1543505072), NCA `755bcf33085ed666cbbcf34de83d1cb0.nca`, a 556,544-byte program NCA with key generation `0x17` (23.0.0) and a 556,032-byte AES-CTR PartitionFS section 0. The `ldn` meta NCA decrypts with `key_area_key_application_00`; its CNMT reports the title version and the program NCA's SHA-256, which matches the local file exactly. Key generation `0x17` needs `key_area_key_application_16`, but the key file stops at `_14` (20.0.0), so the program key area and section cannot be decrypted. The dump contains no `package1`, `package2`, KIP, or other non-NCA file; package1 lives in BOOT0. Static analysis is therefore blocked by **key coverage and artifact completeness**, not just by missing tools. Recorded as `E-083` and in `research/hardware-observations/2026-10-29-firmware-inventory.json`.
29. The **prod-mode** LDN host run on 2026-10-28/29 emitted **373 AES-CTR advertisements** on channel 1. The first captured frame decrypted with the owner's keys and validated its SHA-256; its title, scene, LDN version, security mode, challenge state, participant limit, app version, application-data length, and SSID matched the Phase 1 room. The host logged no `JOIN`, the console reported no rooms after a roughly one-second search, and neither same-phy capture saw a frame from the console. The captures were made on the host's own phy and may include loopback, and `dmesg` logged one more `failed to get tx report from firmware` (3→4), so RF transmission is **not independently confirmed** (`E-084`, `E-085`; `research/hardware-observations/2026-10-29-ldn-prod-host.json`).
30. The macOS **directed** CoreWLAN scan is **invalid** as a TX check. `scanForNetworks(withSSID:)` returned `FOUND` for the room SSID at -90 dBm on channel 6 and -94 dBm on channel 13, both with a nil BSSID, while the host was configured for channel 1. A control scan for a random non-existent 16-byte SSID also returned `FOUND` at -81 dBm on channel 1 with a nil BSSID. A wildcard scan with the host stopped returned 6 results and did not include the host BSSID; that wildcard BSSID check was proposed as the next independent TX check (`E-086`).
31. A **second** approved prod-mode run on 2026-10-28/29 again logged `Advertising now` and `Join events observed: 0`, the console again reported no rooms, and `dmesg` TX-report failures rose from 4 to 5. The wrapper's `tcpdump` processes failed with `Permission denied` on the previous run's tcpdump-owned pcaps, so there is **no valid run-2 capture**; the summary's frame counts and probe output are from run 1. The run is inconclusive and identifies a local wrapper bug, not a console rejection (`E-087`; `research/hardware-observations/2026-10-29-ldn-prod-host-run2.json`).
32. The **wildcard CoreWLAN BSSID check is also invalid** on this Mac without Location Services. Ten scans during the run each reported `BSSID not found in 8 scan result(s)`, but a post-run control scan returned 10 ambient networks and `CWNetwork.bssid` was `nil` for every one. macOS 26.3 is redacting BSSIDs from unpermitted processes, so the comparison cannot distinguish the host from any other network (`E-088`). Granting Location Services to a local scanner later restored real BSSIDs (`E-092`).
33. The **third prod-mode run** on 2026-10-29 again produced no join and no room. The independent Location Services-enabled CoreWLAN scan did not report the host BSSID in 20 scans, although it reported a hidden ambient BSSID on channel 1. The same-phy captures contained only host frames, and each injected frame appeared as a radiotap pair with `txflags=0x0` (`E-089`).
34. The **TP-Link Archer T3U Plus and `rtw88_8822bu` can transmit in AP mode**: a hostapd beacon on channel 1 was received by the Mac at -32 dBm with the adapter BSSID (`E-090`).
35. **Monitor-mode injection on `rtw88_8822bu` does not put frames on the air**: the `ldn` package's `MonitorAP` beaconed a test SSID for 12 seconds, but the Mac did not see it, while the AP-mode control did (`E-091`). The current LDN host uses monitor mode, so its no-room results are explained by the host path, not by a console rejection.
36. **Granting Location Services to a local CoreWLAN scanner restored real BSSIDs** on macOS 26.3: a wildcard scan returned 12 networks with BSSIDs on channels 1, 6, 11, 36, and 100 (`E-092`). The earlier nil-BSSID result (`E-088`) applies to an unpermitted process, not to the API as a whole.
37. **The AP-mode management-frame path has a source-level limit.** Upstream mac80211 can send an AP beacon through `NL80211_CMD_FRAME`, but a non-public vendor action frame on an AP interface needs a station entry; a broadcast destination is not a station, so a broadcast LDN vendor action frame is rejected with `-ENOLINK` (`E-093`). The next AP test must use a unicast vendor action to a known console station or a different adapter/driver.
38. **AP-mode `NL80211_CMD_FRAME` beacon injection works on the adapter.** hostapd 2.11 reached `AP-ENABLED` with `TX10LED-TEST` on channel 1. Twenty `TX10LED-APINJ` beacons submitted through `NL80211_CMD_FRAME` at 100 ms intervals were seen by the Mac at -28 dBm with the adapter BSSID in all 12 Location Services-enabled scans, alongside the hostapd beacon, while ambient networks remained visible. The adapter was restored to monitor mode (`E-094`). This resolves the beacon half of the AP path; the vendor-action half still needs a station entry (`E-093`).
39. **The unicast vendor-action path is accepted by the kernel.** The owner approved a 5-frame control. `Firmware/ap_unicast_run.sh` started hostapd with `TX10LED-TEST` on channel 1; `Firmware/ap_unicast_test.py` added a temporary station entry for the console's MAC, submitted five unicast vendor actions with the non-LDN test OUI `00:11:22` and payload `TX10LED-UNICAST`, removed the station entry, and restored monitor mode. All five requests returned without a netlink error (`E-095`). This confirms the kernel-level station-lookup half of the AP path, but not that the console received the frame or that its LDN parser reacted.

40. **The real LDN unicast path is accepted by the kernel, but reception is unobserved.** The owner approved a 60-second real LDN run. The first attempt sent 0 advertisements because the driver rejected the broadcast-BSSID action frame with `EINVAL`. A diagnostic isolated the rejection: the 1,388-byte LDN frame and a 42-byte control both failed with a broadcast BSSID and succeeded with the AP BSSID; all beacon variants, including the 89-byte null-SSID LDN beacon, were accepted (`E-097`). The rerun used the AP BSSID and submitted 568 valid AES-CTR advertisements plus 568 null-SSID beacons at 100 ms intervals; all requests returned without a netlink error, the station entry was removed, and monitor mode was restored (`E-096`). The console was off/away, so no room appearance or parser reaction was observed; the run is inconclusive for the LDN hypothesis. `dmesg` reported `failed to get tx report from firmware` and, after hostapd stopped, a firmware download failure; the adapter required a USB deauthorize/reauthorize cycle before it probed cleanly again.

41. **The AP path cannot reproduce the original broadcast-BSSID advertisement.** `rtw88_8822bu` rejects any action frame with a broadcast BSSID with `EINVAL`, even after a temporary station entry is added; the same frame with the AP BSSID is accepted (`E-097`). The real LDN advertisement uses a broadcast BSSID, so the AP unicast variant differs from the original. The supervised rerun answered the room-appearance question: the console displayed `TX10LED`, so the AP-BSSID advertisement is accepted by the scan path.
42. **The supervised AP-mode rerun reached the scan path but not the join path.** On 2026-10-29 the console displayed the advertised room `TX10LED`; selecting it produced `2203-0065` immediately, the search screen closed, and the console returned to the game normally. hostapd logged only `AP-ENABLED` and `AP-DISABLED`, with no authentication, association, or station event (`E-098`). The hostapd WLAN SSID was `TX10LED-TEST` with open security, not the room's 32-character hexadecimal WLAN SSID and LDN RSN IE, so the failure is consistent with a host-configuration mismatch before association. The console stayed responsive; this is not evidence of a parser fault.
43. **The third AP-mode run is negative for the current hostapd/AP path.** With the association-response RSN IE omitted and the raw authorized-station `0x88B7` path enabled, the console authenticated, associated with AID 1, and was authorized, then sent one 28-byte null-data frame and disassociated with reason 8 about 1.4 seconds later. The pcap contains no console data payload frame and no `0x88B7` request; the owner saw `2203-0066` and the game returned normally (`E-101`). The parser hypothesis remains untested; a materially different AP implementation or adapter/driver is needed.
44. **The read-only GameShare/`splay` review found no public vulnerability and no post-20.0.0 `splay` security fix.** The reviewed sources contain no `splay`/GameShare advisory or exploit. 23.0.0 updated `splay`'s NPDM (`FsAccessFlag` bit 47, `news:c`, `stpl:sys`, KernelVersion 27.1) and RomFS (`lyt`, `message`, `sound`), but recorded no security fix; 23.0.1 updated only `sdb`, not `splay` (`E-102`). This is an absence-of-documented-method finding, not proof that `splay` is safe.
45. **The 76 program NCAs split by key generation into `0x07`:1, `0x15`:1, `0x16`:7, and `0x17`:67.** The only `0x15` program is `miiEdit` (`0100000000001009`), which decrypted with `key_area_key_application_14` and verified its section-0 master hash; it is a Mii editor applet, not a remote-input surface. `splay`'s program NCA is key generation `0x17` and remains encrypted, but its `0x00` meta CNMT is readable and matches the program NCA (`E-103`).
46. **The modded 23.0.1 source console is no longer available.** The owner retains a modded 22.0.0 Switch and the unmodded 23.0.1 target. The existing 23.0.1 NCA dump and keys remain valid local artifacts, but a matching 23.0.1 BOOT0/package1 dump and key generation `0x17` keys cannot be produced from the remaining hardware. The 22.0.0 console will be left untouched; it cannot supply 23.0.1 artifacts, and its keys do not cover generation `0x17`.
